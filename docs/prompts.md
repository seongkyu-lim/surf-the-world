# 프롬프트 모음

이 프로젝트에 실제로 쓴 프롬프트를 순서대로 모았다. 그대로 복사해서 `< >` 부분만 바꿔 쓰면 된다.

프롬프트는 일부러 짧다. 형식과 규칙은 저장소의 [`BRIEFING_GUIDE.md`](../BRIEFING_GUIDE.md)와 [`SOURCES.md`](../SOURCES.md)에 있고, 프롬프트는 "그 파일을 읽고 따르라"고만 한다. 이렇게 하면 형식을 바꿀 때 예약 작업을 건드리지 않고 파일만 고치면 된다.

## 1. 프로젝트 설명 (관심 분야)

claude.ai에서 프로젝트를 만들고 설명란에 관심 분야를 적는다. Claude가 이 내용을 읽고 브리핑 구성을 잡는다. 주제를 구체적으로 쓸수록 결과가 좋다. "경제"보다 "금리·환율, 물가"가 낫다.

```text
경제: 금리·환율, 물가, 증시, 부동산·주거, 세금·연말정산
정치·사회: 국내 정치, 정책·법안, 국제 정세, 노동·교육
가정·생활: 육아·교육 정책, 주택·청약·대출, 보험·연금, 건강
재테크: 투자 기초, 절세, 연금·노후 준비
산업·기술: AI, 반도체, 블록체인·디파이 (이쪽은 이미 강점이니 비중은 작게)
국제·문화: 미국·중국 이슈, 에너지·기후, 인구·저출생 같은 사회 트렌드
교양: 역사, 심리, 책 추천
```

이미 잘 아는 분야는 "비중은 작게"라고 적어 두면 분량이 그쪽으로 쏠리지 않는다.

## 2. 구성 설계 요청

프로젝트 안에서 새 대화를 열고 다음과 같이 요청했다.

```text
내가 프로젝트 설명에 세팅한 관심사로 매일매일 브리핑 받고 싶어.
어떻게 구성하고 어떻게 유익한 정보를 얻고 제공할 수 있을지 고민해서 계획 알려줘.
추가로 정보는 정적 깃허브 페이지 만들어서 너가 거기 매일매일 업로드하면 좋겠다.
```

여기서 나온 계획이 "매일 고정 코너 + 요일별 심화 코너 + 추적 이슈 파일" 구조다.

## 3. 구축 요청

빈 공개 저장소를 만들어 주소를 주고 다음과 같이 요청했다.

```text
https://github.com/<아이디>/<저장소>.git
이거야. 진행해줘.
그리고 해당 구축 과정을 나와 같은 수요가 있는 사람들을 위해
프롬프트나 구축 과정 같은 걸 깃허브에 같이 보관하면 좋을 것 같아.
```

## 4. 출처 기준 요청

첫 브리핑이 나온 뒤 출처 품질을 따로 요청했다. 이 요청으로 [`SOURCES.md`](../SOURCES.md)가 만들어졌고, 첫 브리핑의 출처도 발표 기관 원문 위주로 바뀌었다.

```text
출처가 되는 곳이 얼마나 퀄리티 있는 곳인지가 중요하다고 생각해.
꼼꼼히 검토해서 가장 유명하고 신뢰성 있고 가치가 있는 출처를 검토해줘.
```

처음부터 3번 요청에 이 문장을 붙이면 한 번에 끝난다.

## 5. 매일 실행되는 예약 작업 프롬프트

예약 작업은 매번 아무 기억이 없는 새 세션에서 시작한다. 그래서 프롬프트 하나만 읽고도 일을 끝낼 수 있게 썼다.

```text
"세상 읽기" 데일리 브리핑을 한 편 작성해 GitHub Pages 사이트에 발행한다.

1. GitHub 저장소 <아이디>/<저장소>를 푸시 권한으로 이 세션에 추가하고 클론한다.
2. 저장소의 BRIEFING_GUIDE.md와 SOURCES.md를 끝까지 읽는다. 형식, 요일 코너,
   출처 등급, 품질 규칙은 모두 그 두 파일을 따른다.
3. 한국 시간(Asia/Seoul) 기준 오늘 날짜와 요일을 확인한다.
4. BRIEFING_GUIDE.md의 "매일 실행 순서"대로 진행한다: tracking.md, glossary.md,
   최근 3일 치 브리핑을 읽고, 웹 검색으로 최근 24시간 기사와 공식 발표를 모아
   원문에서 숫자를 확인한 뒤, _posts/YYYY-MM-DD-briefing.md를 쓰고
   tracking.md와 glossary.md를 갱신한다.
5. "발행 전 점검"을 통과하면 main 브랜치에 커밋하고 푸시한다. 강제 푸시는 하지 않는다.
6. 마지막에 브리핑 제목과 사이트 주소(https://<아이디>.github.io/<저장소>/)를
   한 줄로 알린다.

지켜야 할 것:
- 원문에서 확인하지 못한 숫자는 쓰지 않는다. 웹 검색이 되지 않으면 브리핑을
  지어내지 말고, 발행하지 않은 채 이유만 알린다.
- 같은 날짜의 브리핑 파일이 이미 있으면 새로 쓰지 않고 그 사실을 알린다.
- 공개 저장소이므로 독자 개인의 정보는 쓰지 않는다.
- 푸시가 실패하면 원인을 알리고 멈춘다.
```

## 프롬프트를 고칠 때

| 바꾸고 싶은 것 | 고칠 곳 |
|---|---|
| 관심 분야, 분량, 코너 구성, 말투 | `BRIEFING_GUIDE.md` |
| 믿을 출처와 쓰지 않을 출처 | `SOURCES.md` |
| 받는 시간 | 예약 작업의 일정 |
| 저장소 주소 | 예약 작업 프롬프트 |

브리핑이 마음에 들지 않을 때는 "오늘 브리핑의 이 부분이 이래서 별로였다. 작성 규칙을 고쳐 줘"라고 요청하면 된다. 규칙 파일이 바뀌면 다음 날부터 반영된다.
